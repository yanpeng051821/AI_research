# Pretrain 512：数据切分快照

> 历史记录：2026-10-21。仅完成 512 长度小样本的数据准备与切分，没有执行对应正式训练。该方案已被完整 mini 来源、长度 768 的方案替代，不再作为当前操作步骤。

## 1. 方案范围

固定来源为 jingyaogong/minimind_dataset，revision 为 `312afb4f76391145c6902f765bb51691c09a12f5`，文件为 pretrain_t2t_mini.jsonl。从完整来源按 seed=42 选取 10,000 条候选；正文大于 510 tokens 的记录整条过滤，再应用 12 条内容复核决定。

得到训练 8,907 条、验证 500 条、排除 593 条。排除项包含 590 条超长记录和 3 条人工排除记录；9 条已审保留记录固定用于训练，验证抽样 seed=43。正文保持原样，输出按来源行号排序。

这份归档用于解释已做过的工程练习，不是第二条训练路线。当前正式流程见[第七周教程](../../practice_notes/week_07_pretrain_experiment.md)。

## 2. 文件与来源

本目录保存适合 Git 跟踪的少量元数据：

- data_manifest.json：输入、tokenizer、构造脚本与输出身份，以及切分规则和统计。

人工决定是已有复核结果，不由抽样脚本自动重建。新机器先按第七周教程第 3 节恢复并核验原始来源、候选和分析产物，再使用这里保存的 review_decisions.jsonl。字段快照不能代替原始文件的字节身份。

## 3. 当时的长度选择

| 指标 | 结果 |
| --- | ---: |
| 正文 token 总数 | 2,584,015 |
| 平均正文长度 | 258.4015 |
| 最短 / 最长 | 6 / 6,287 |
| P50 / P90 | 210 / 414 |
| P95 / P99 | 557 / 约 1,416.03 |
| 完全重复的额外记录数 | 0 |

| 候选 max_length | 正文容量 | 完整容纳记录 | 整条过滤记录 | 整条过滤的正文 token 占比 |
| ---: | ---: | ---: | ---: | ---: |
| 512 | 510 | 9,410，94.10% | 590 | 24.08% |
| 1,024 | 1,022 | 9,664，96.64% | 336 | 17.89% |

“整条过滤”与“截断尾部”不能混用：512 下若只截尾，损失约 12.44% 正文 token；若排除整条超长记录，损失约 24.08%。1024 下对应约 4.60% 与 17.89%。长记录数虽少，承载的 token 较多。

最初讨论曾考虑优先测量 1024，随后学习者指出长度翻倍仅额外容纳 254 条记录。两组保留正文约为 196 万与 212 万 tokens，有效正文增加约 8.2%；若分别用当前定长 collator 处理一轮，序列位置总量却约为 482 万与 990 万。位置数量不等于实测耗时，但揭示了 padding 成本。本次以完整工程和预算控制为主，最终确认采用 512，不额外安排 1024 对照训练。上表保留作为选择依据。

本次正文上限为 510，超过上限整条排除，其余记录保留原文，不切块、不截尾；现有 9410/590 清单用于这一步。记录数覆盖与 token 损失一并披露，结论限于较短文本。这是当时采用的规则；当前正式方案不使用这份切分。编码器仍有截断保护，切分时重新编码核验长度，确保本次保留记录不实际触发截断。

## 4. 构造与重建

### 4.1 输入与处理顺序

实现为 [build_pretrain_splits.py](../../implementation/scripts/build_pretrain_splits.py)。学习者写了读取清单的开头，随后明确委托助手完成本步，助手编写过滤、切分、落盘与测试；不将本步记为学习者独立实现。

输入为候选正文、来源 manifest、分析报告、两份长度清单和 review_decisions。流程顺序为：

~~~text
核验候选哈希与记录身份
→ 重新编码，确认长度清单没有过期
→ 按 source_line 合并正文、长度和审查决定
→ 9,410 条长度合格记录减去 3 条人工排除
→ 9,407 条可切分记录
→ 9 条已审保留固定训练，其余 9,398 条作为验证抽样池
→ seed=43 抽取 500 条验证，剩余 8,907 条训练
→ 保存正文、排除清单和 manifest
~~~

这里要先解析 JSON，再取整数 source_line。直接把文件中的 line 加入 set，得到的是 JSON 字符串集合，无法与候选中的整数行号匹配。

### 4.2 核验与关键代码

read_records 复用 iter_jsonl，解析失败就报告路径与行号；index_by_source 将记录组织为来源行号到记录的映射，并拒绝重复行号。构造脚本检查候选 SHA256、审查指向的候选与正文 SHA256、来源版本，以及两份长度清单是否完整分流。

脚本用当前本地 tokenizer 对全部候选重新编码，验证长度与 report 一致；防止沿用旧长度清单。正文完全重复则停止，要求先处理分组。本次不声称完成近似重复或原始文档分组隔离。

核心筛选与切分关系为：

~~~python
eligible_lines = set(retained) - excluded_lines
validation_pool = sorted(eligible_lines - train_only_lines)
validation_lines = set(random.Random(seed).sample(validation_pool, validation_size))
train_lines = eligible_lines - validation_lines
~~~

三个集合分别表达长度合格、内容排除和已经参与内容讨论的保留记录。验证抽样前先排除 train_only_lines。正文输出继续按来源行号排序，随机训练消费顺序留给 sampler；切分随机种子与训练随机种子是不同职责。

### 4.3 运行与输出

在 implementation 目录执行：

~~~powershell
uv run --locked python scripts/build_pretrain_splits.py
~~~

输出目录必须不存在。已有目录会被拒绝，复练使用新的目录，例如：

~~~powershell
uv run --locked python scripts/build_pretrain_splits.py --output-dir data/processed/pretrain_512_rebuild
~~~

~~~text
data/processed/pretrain_512_v1/
  train.jsonl
  validation.jsonl
  exclusions.jsonl
  manifest.json
~~~

训练与验证每行包含 source_line 和原始 text；现有 Dataset 只编码 text，来源字段用于追溯。exclusions 保存来源、正文哈希、长度与排除原因。manifest 保存所有输入文件、tokenizer JSON 资产、构造脚本和三份输出的哈希，以及规则、计数和 token 预算。

脚本在输入校验完成后才创建输出。若写文件阶段因磁盘等问题中断，可能留下不完整的新目录；不会覆盖已有数据，但不能把目录存在当作构造成功，需以完整 manifest 与文件哈希判断。

### 4.4 实际结果与验证理由

| 分组 | 记录数 | 正文 tokens | shift 后有效目标 tokens |
| --- | ---: | ---: | ---: |
| 训练 | 8,907 | 1,860,620 | 1,869,527 |
| 验证 | 500 | 100,545 | 101,045 |
| 排除 | 593 | 不参与更新 | 不参与评测 |

shift 后计数为正文 token 数加记录数：每条先加 BOS/EOS，再 shift，目标包括正文和末尾 EOS，不包括最前 BOS。实际遍历验证 Dataset/collator 得到 101,045，与 manifest 一致。表中训练 token 数是一轮数据消费的数量，不代表模型已经训练。

独立核验训练、验证和排除集合互不交叉，合起来覆盖 10,000 条候选；保留正文与来源完全相同，训练和验证没有完全相同的正文，9 条已审保留只在训练中。另一个临时目录重建后，四份输出逐字节一致。这个结果限于当前输入与环境，不承诺任意 Python/tokenizer 版本均得到相同产物。

[test_pretrain_splits.py](../../implementation/tests/test_pretrain_splits.py) 的 6 项测试覆盖分流与重建、候选篡改、过期审查身份、过期长度、覆盖保护及验证抽样池约束。测试使用小型字符 tokenizer 隔离文件与切分行为；真实 tokenizer 和现有数据管线另在上述实际产物上核验。2026-10-21 全项目结果为 255 passed。

## 5. 验证设计的历史讨论

> 以下保留当时围绕 500 条验证记录的讨论；其中“当前”“待确定”均指该历史方案。正式方案已固定 5,000 条验证记录，操作说明见第七周教程第 4.2、6.3.4 节。

### 5.1 评估目的与目标分布

划分前先说清验证结果要回答什么。当前目标是检查模型对相同来源、较短文本分布的预测是否改善，所以从采用相同处理规则的候选池中随机留出记录。这属于同分布验证。

如果问题改成“数学语料训练后能否改善代码能力”，就需要另设代码评测数据；如果关心新时间段、不同用户或新机构上的效果，应按对应时间或实体划分。这些分布变化可以是有意设计的实验条件。不能把“验证集必须与训练集相同分布”当作所有实验的前提。

同源随机抽样只提供近似同分布的机会，不能保证每个有限样本的配比相同。除了全局 NLL，还应根据任务关注长度、语言、主题、来源及质量的组成。记录占比相近也不等于 token 占比相近，少量长记录可能对 token 加权指标贡献很大。

本次已确认两组来源相同、处理规则相同，并保留实际长度与 token 数；尚未系统标注和检验语言、主题及质量配比，不能声称代表性已被充分证明。

### 5.2 划分单位与内容泄漏

“不重复”至少要分三个层次。第一层是记录身份不交叉；第二层是正文不完全相同；第三层是近似重复、共享段落或同一原始文档/对话派生的内容不跨组。换标点、改空格、改写一句话，可能使文本哈希不同，但模型仍可能见过非常接近的内容。

获得可靠原始文档、对话或任务组 ID 时，应先以这些来源分组切分，再在组内切块、派生问答或生成候选回答。若先切块再随机分配，原文相邻段落或重叠窗口可能进入不同组。时间泛化等任务还应防止未来信息进入训练。

本次以候选记录及 source_line 为单位，已检查身份不交叉和精确正文不重复。source_line 只标识来源文件中的记录，不等于原始文档或对话 ID；部分记录又有拼接，因此严格同源隔离与近似去重仍是限制。不能仅凭三个集合互斥宣布完全没有泄漏。

### 5.3 验证规模、噪声与运行成本

本次留出 500 条，约占可用记录的 5.3%，实际产生 101,045 个有效目标 token。它是保留训练数据、覆盖一定文本量和控制验证成本之间的初始选择，没有经过“该比例最优”或“统计精度足够”的证明。

规模是否足够取决于要检测的变化。观察初始化到训练后的明显 NLL 变化，与区分两个配置相差 0.005 的 NLL，所需精度不同。token 属于同一文本时彼此相关，不能把 10 万个 token 简单当作 10 万次独立观测。

需要解释小差异时，应保存逐记录 loss_sum 与 valid_tokens，在相同记录上进行配对比较。若估计抽样不确定性，可以按记录或已知来源组重采样，每次重新计算总 loss_sum / 总 valid_tokens；这与训练随机种子的变化是不同不确定性。当前没有为结果计算区间，也没有运行多 seed 训练，不能预先断言微小改善显著。

验证频率、每次评估的数据量与整份验证集大小是三个选择。频繁评估会消耗训练预算；随机取少量 batch 又会增加比较噪声。当前实现遍历全部固定验证记录，先以稳定比较为主，执行频率待短跑实测后确定。

### 5.4 数据处理与计分口径

比较两个 checkpoint 时，验证文件、tokenizer、特殊 token、长度策略、截断或过滤规则、attention mask、监督 mask 与 causal shift 必须使用相同约定。否则指标变化可能来自评测方式变化。比较不同训练方法时训练侧可以按实验设计变化，但共同验证合同仍要明确；故意更换 tokenizer 等情况不能直接把原始 per-token NLL 当成同一指标。

当前验证使用 token 加权平均：

~~~text
validation NLL
= 所有验证记录的 loss_sum 总和
  / 所有验证记录的有效目标 token 总和
~~~

不要直接平均每个 batch 或每条记录的平均 loss，除非目标本来就是“batch 等权”或“记录等权”。短记录与长记录有效 token 数不同，直接平均会改变权重；padding 位置也不能计入分母。所有验证记录都应被消费，不能因最后一个 batch 不满而静默丢弃。

本次 [evaluate_nll](../../implementation/src/minimind_lab/training/evaluate.py) 采用 sum/count 汇总，现有切分已用真实 Dataset/collator 验证有效 token 总量。后续需将数据及配置身份检查接入实际训练入口，防止运行时拿错文件；manifest 保存了身份并不等于入口已经强制校验。

### 5.5 推理模式与训练状态

验证时调用 model.eval()，让 Dropout 等组件采用评估行为；再用 torch.no_grad() 关闭梯度图记录。eval() 不等于冻结参数，no_grad() 也不自动切换模型模式；二者负责不同事情。

验证不执行 backward 或 optimizer.step，不推进训练 scheduler 与训练 sampler。结束后应恢复原先的 training 模式，包括异常路径。涉及随机预处理或随机验证抽样时，还要明确随机状态是否影响后续训练，必要时使用独立生成器；不能仅以没有 backward 推断训练轨迹绝对未被影响。

当前 evaluate_nll 保存并在 finally 中恢复模型模式。评测的完整设备、精度、频率和数据加载配置仍待本次运行合同确定。

### 5.6 开发验证与最终测试

验证集本来可以用于观察曲线、选择 checkpoint 和调整超参数；固定验证数据不表示不能参考其结果作开发决策。但反复尝试并总挑验证分数最高的配置，会使这个分数对最终效果的估计更乐观。若要给出独立的最终能力结论，需要未参与这些选择的测试数据或外部任务。

不能把困难记录从验证集中删除、换一个更有利的 seed，随后仍当作同一次合同下的改善。发现真实数据错误时，应记录原因、更新数据版本并重新评估受影响的对照，避免只给某个 checkpoint 换题。

人工查看验证文本不自动使其失效。关键在于有没有据此定制规则、提示、数据或模型选择。本次 12 条用于讨论清洗与处理规则，因此作保守安排：3 条排除，9 条保留只进训练。train_only_lines 是这个特殊集合，不是全部合格数据。

本次验证集用于开发监控，没有另建独立最终测试集。原始语料也存在质量问题：即使分布匹配、无泄漏，模型更接近错误参考文本仍可能降低 NLL。可靠知识或推理能力需要另外设计可靠任务与评分证据。

### 5.7 公开实践与本次选择

以下为公开资料中的具体实践，不是通用最优比例证明：

| 来源 | 明确披露的做法 | 对本次的参考 |
| --- | --- | --- |
| [DeepSeek LLM，第 3.2 节](https://arxiv.org/pdf/2401.02954#page=11) | scaling 实验使用独立、与训练分布相似的 100M-token 验证集 | 说明绝对规模、分布和用途；不能扩展成全部 DeepSeek 模型的统一配置 |
| [nanoGPT：OpenWebText](https://github.com/karpathy/nanoGPT/blob/master/data/openwebtext/prepare.py) | 随机留出 0.05% 的文档，固定 seed；注释给出约 4,007 篇、443 万验证 tokens | 大语料的小比例仍可有较大绝对规模 |
| [nanoGPT：Shakespeare 字符模型](https://github.com/karpathy/nanoGPT/blob/master/data/shakespeare_char/prepare.py) | 连续文本前 90% 训练、后 10% 验证，约 11.15 万字符 tokens | 小型示例使用不同规模和切分单位，不应直接照搬其比例 |
| [nanoGPT：训练循环](https://github.com/karpathy/nanoGPT/blob/master/train.py) | 默认每 2,000 次训练迭代评估一次，评估时各取 200 个 batch 估计 train/val loss | 验证总量、每次评估量与频率需要分别决定；配置可覆盖默认值 |
| [OLMo，第 2.4 节](https://arxiv.org/pdf/2402.00838#page=4) | 训练内任务评测每 1,000 step 执行；另用覆盖多个来源与领域的 Paloma，并清除训练中的评测段落重合 | 比例之外，评测覆盖、频率和去污染同样重要；任务评测不等于同分布验证 NLL |
| [DeepSeek-V3，第 4.5.3 节](https://arxiv.org/html/2412.19437v2#S4.SS5.SSS3) | 小模型消融报告 validation loss；所查报告未见其预训练验证集具体划分比例 | 没有披露的参数不能按经验替作者补全 |

当前保留 500 条作为第一轮实验起点，后续用实际耗时、逐记录结果和需要判断的变化量检查是否够用。统计 token 数相近不说明 tokenizer、内容、相关性和评估精度相同，也不意味着我们的方案已经得到这些项目的直接验证。

## 6. 归档边界

真实正文位于 Git 忽略目录，Git 中只有少量元数据、人工决定和重建说明；推送本目录不代表备份了完整数据。来源、候选、分析报告和数据 manifest 的 hash 对应各自原始字节，不能将重新排版的字段快照当作相同文件。

这份记录仅说明旧方案的数据工程检查结果，不证明模型经过训练，也不证明语料事实正确、近似内容独立或可直接进入正式实验。
