## 1. 目的与选择

校准要回答的是：同一套标准能否解释具体问题，处理动作是否有足够依据。不是用三条样本评估 905,718 条数据的总体质量。

样本来自固定 seed=20261029 的分组观察文件，先预览后按对比价值挑选，分别覆盖内容正确、缺失输入、工具协议不一致。选择有意偏向能解释差异的案例，不能计算总体问题率。

原文包在 implementation/data/processed/sft_candidate_inspection_v1 下，各记录附来源行和原行 SHA256。这里只摘必要证据，完整来源身份继承[结构报告](../full_structure_v1/structure_report.json)。行号从 1 开始，消息索引从 0 开始，原行 hash 包含源文件换行。报告不是原始数据备份。

## 2. 集合计算：内容层面建议保留

来源行 99,806，plain_examples.jsonl。用户提供 `[1,2,3,4,5]`、`[3,4,5,6,7]`，要求并集和交集。助手给出并集 `[1,2,3,4,5,6,7]`、交集 `[3,4,5]` 并解释方法。

使用独立编写的集合计算核对，而不是执行语料附带的代码：

```python
a = {1, 2, 3, 4, 5}
b = {3, 4, 5, 6, 7}
assert sorted(a | b) == [1, 2, 3, 4, 5, 6, 7]
assert sorted(a & b) == [3, 4, 5]
```

输入充分，结果与方法相符，因此 C02、C03、C04 在本例范围内通过，建议内容层面保留。Python set 的打印顺序不保证，核对的是集合元素，不把某种显示顺序当成接口承诺。模板、长度和切分未检查，不表示整条已正式接受。

## 3. 缺失代码：建议排除原样

来源行 731,011，reasoning_only_examples.jsonl。完整记录只有一条用户消息和一条助手消息，没有更早代码上下文。

- 用户：“下面的代码运行结果是什么？”
- 助手：“第三行的计算是 10 + 20 = 30，输出30。”并声称第四行输出变量 a 的值，给出 `30`、`10`。
- reasoning_content 也自行描述了 a=10、b=20 等程序内容。

问题不是加法错误，而是没有程序却编造输入与结论。C02、C03、C04 不通过，建议排除原样。若另行制作澄清输入的示范，需要明确记录为新修订，不得静默给用户补造代码。

不要推广成看到“下面代码”就排除：其他多轮对话可能在前文已经提供代码。本例判断依据是完整记录确实缺少对应输入。

## 4. 未声明工具：建议排除原样

来源行 776,360，tool_only_examples.jsonl。消息 0 声明 `get_current_time` 与 `unit_converter`。用户询问北京天气及摄氏温度换算，消息 2 却调用 `get_current_weather`，随后提供工具结果和最终回答。

JSON 能解析，调用和结果也存在，但所调用的天气工具不在声明中，F02 不通过，相关能力示范 C05 不通过。不能为了让样本通过而自行补上虚构工具声明。

工具结果提供 15°C，助手换算为 59°F；独立计算 `15 * 9 / 5 + 32 == 59` 成立，但局部正确不能抵消协议错误。天气事实未独立核实，不以当前日期的天气反证历史示例。

消息 2 的 content 为空不是此次判错依据。该例恰好说明：空正文可以属于工具动作，仍要检查工具是否真的可用、参数和结果是否匹配。不能据此排除全部工具样本。
