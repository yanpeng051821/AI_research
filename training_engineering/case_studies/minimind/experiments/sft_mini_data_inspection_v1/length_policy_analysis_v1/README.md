# SFT 长度处理影响分析

> 分析已完成，未选择正式长度或执行任何过滤、截断。统计基于当前未完成内容筛选、去重与身份修订的完整候选；最终派生数据变更后需要重新统计。

## 1. 问题与比较对象

全量预检给出了超长记录数，但它没有回答：处理这些记录会失去多少助手监督，是否破坏完整回复。本次比较四个候选长度 768、1,024、1,536、2,048，以及两种最直接的处理：

- 整条排除：完整编码长度大于上限时，该记录全部不纳入。
- 前缀切片：保留 input_ids[:limit]、labels[:limit]，不补 EOS、不改变已有标签。

这里只模拟影响，不是输出处理后的训练文件。完整轮次裁切、对话分块、packing 等方案不在本次分析范围，不能把结果解释为只有上述两种可行方案。

## 2. 方法与复跑

入口为 [analyze_sft_length_policies.py](../../../implementation/scripts/analyze_sft_length_policies.py)。先核对[全量编码报告](../full_encoding_preflight_v1/report.json)、逐条明细、源文件、编码代码和 tokenizer 身份。整条排除使用全量明细的记录长度和助手目标数；前缀切片需要知道目标具体位于哪里，因此重新编码超过最小候选长度 768 的 49,187 条，而不是假定尾部 token 全都被监督。

```powershell
# 在 implementation 目录运行，复跑时更换新的 report-dir。
uv run --locked python scripts/analyze_sft_length_policies.py `
  --source data/raw/minimind/sft_t2t_mini.jsonl `
  --encoding-report ../experiments/sft_mini_data_inspection_v1/full_encoding_preflight_v1/report.json `
  --report-dir ../experiments/sft_mini_data_inspection_v1/length_policy_analysis_v1 `
  --limits 768 1024 1536 2048
```

每条重新编码的长度和 shift 后目标数都与既有明细对照；读取源行时核对原行 hash，读完核对整文件 hash、总行数、代码和报告身份。基线必须已经全部编码且无诊断标记，避免悄悄只在可编码子集上统计。实际分析约 78.25 秒，没有模型前向或 GPU 执行。

输出 [report.json](report.json) 保存两种处理的总体及按形态分组影响、少量截止点案例和方法/身份；不保存新的训练数据或大明细副本。

## 3. 整条排除的影响

基线为 905,718 条、377,330,100 个有效助手目标。下表的两个比例分别以基线记录数、基线助手目标数作分母，不是同一个口径。

| 长度 | 不纳入的记录 | 占全部记录 | 不纳入的助手目标 | 占全部助手目标 |
| --- | --- | --- | --- | --- |
| 768 | 49,187 | 5.431% | 36,978,625 | 9.800% |
| 1,024 | 3,395 | 0.375% | 3,914,726 | 1.037% |
| 1,536 | 531 | 0.059% | 892,154 | 0.236% |
| 2,048 | 73 | 0.0081% | 160,859 | 0.0426% |

长记录往往包含更多监督位置，所以排除的记录比例小，不代表失去的监督比例同样小。这里的“目标数量”也不等于知识价值：目标包含当前保留的思考、正文和结束标记，内容质量仍需另查。

处理还会改变形态分布。以 768 为例：按各组自身记录数计算，plain 排除约 2.80%，reasoning_only 排除约 11.72%，tool_only 排除约 2.09%；思考标记组自身的助手目标约少 17.13%。不能把统一长度过滤误认为对所有样本类型影响相同。1,024 下三组分别少 2,234、1,154、7 条；这些是原始形态标记，不是人工核实的领域或难度标签。

## 4. 前缀切片的影响

| 长度 | 被切片记录 | 丢失的尾部助手目标 | 切在助手区间且未保留其 EOS | 切片后零目标记录 |
| --- | --- | --- | --- | --- |
| 768 | 49,187 | 4,713,661 | 45,864 | 7 |
| 1,024 | 3,395 | 828,597 | 3,319 | 2 |
| 1,536 | 531 | 130,587 | 529 | 0 |
| 2,048 | 73 | 14,546 | 73 | 0 |

切片比整条排除保留了更多目标，但保留下来的示范可能没有完整结尾。这里不是说截断必然导致训练失败，而是它改变了监督内容，不能只按保留 token 数判断优劣。

在 1,024 下，3,395 个截止点进一步分为：

- 3,319 条位于连续助手监督区间内，当前回复的 EOS 尚未保留。
- 21 条已经保留助手 EOS，只丢了其后的换行，不计作上一类。
- 55 条切在助手监督区间之外；这不等于没有影响，可能丢掉后续回复、用户消息或工具轨迹的一部分。

判定依据是当前 labels 中的连续监督区间与 EOS，不声称完成了截断后完整工具轨迹的审核。报告使用 `assistant_without_eos`、`assistant_eos_without_newline`、`outside_assistant_supervision` 分别记录，不能将三者合并称为“回答被截断”。

零目标也必须在处理之后重新检查。源行 88,237（原长 1,138、57 个目标）和 157,496（原长 1,122、64 个目标）原来均有监督，但保留前 1,024 个位置后均为零目标；两条已独立重新编码核对。768 下共 7 条，1,536/2,048 下为 0。原始全量预检的零目标数为 0，并不能保证经过某种处理后仍为 0。

不能将被切掉的内容靠补一个 EOS 恢复。本次没有补 EOS；任何“截断后强制结束”的方案都会改变示范，需要另行定义、检查和评估，不能作为无说明的修复。

## 5. 验证与待决事项

8 项定向测试通过（3.38 秒），覆盖目标计数、shift、缺失 EOS 与仅丢换行的区别、截在上下文、丢后续轮次、比例分母及非法长度/对齐。全项目 414 passed（77.11 秒，与分析并行运行）。

分析后独立重读全量明细，核对每个长度的整条排除数量、目标数及分组加总；切片截止类别数量之和等于被切片数，切片丢失目标不超过整条排除目标。还按“所有目标可能都在尾部”的必要条件筛选候选并重新编码，独立复现全部零目标条数及上述源行。

从当前数据保留角度，1,024 加整条排除超限记录值得作为优先讨论的候选：比 768 少损失很多监督，也不人为制造半段回复。它不是已经接受的配方；固定 padding 变长会增加开销，最终还需结合模型、显存、吞吐及训练目标判断。

本次没有决定长度、生成训练/验证集、改写身份或启动训练。内容与完整工具协议审核、重复与隔离处理仍未结束；数据范围或编码规则变化后，这些数字也必须重新计算。
