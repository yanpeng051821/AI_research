# 完整候选数据编码预检

> 2026-10-30 完成。905,718 条全部成功编码，当前诊断项未检出异常；实际耗时约 279 秒。运行完成、源行明细及样本交叉核对通过，不宣称内容质量或完整工具协议通过。

## 1. 目的与输入

此前 1,000 条随机样本用于确认检查入口和初步观察分布，不能代替全部实际输入的验收。本次将相同的工作编码规则应用到完整候选文件，获取全量编码异常、长度和助手目标统计；以后构造最终派生数据后，仍需对最终文件重新核验，不能用原始候选的报告代替派生产物验收。

来源为 `jingyaogong/minimind_dataset` 的 `sft_t2t_mini.jsonl`，固定 revision `312afb4f76391145c6902f765bb51691c09a12f5`，共 905,718 行、1,739,201,170 字节。完整 SHA256 为 `abb1e76b2056e14728beb78db96b7b3c491a0bef1ed3e34a9b381b28f29fa518`，参照[来源结构报告](../full_structure_v1/structure_report.json)。

## 2. 实现与执行

入口 [inspect_sft_full_encoding.py](../../../implementation/scripts/inspect_sft_full_encoding.py) 先核对整文件大小和 hash，再逐行读取原始字节，以固定大小分块交给 CPU worker。每条使用同一基础 validator、字段转换与 `encode_sft_conversation`；边界扫描和分位数函数复用已有样本预检入口，不修改其源码或原报告身份。

处理步骤为：

```text
来源大小与 SHA256 核对
  -> 按行读取、记录原行 hash，重新统计读取字节的整文件 hash
  -> 分块交给 worker：基础结构 -> 字段转换 -> 边界观察 -> 编码 -> 目标计数
  -> 按源顺序写逐条明细与异常明细
  -> 汇总长度、目标、形态与候选长度超限条数
  -> 核对输入总行数、文件 hash、代码及 tokenizer 身份
  -> 最终报告与运行完成标记
```

在 implementation 目录的 PowerShell 执行：

```powershell
uv run --locked python scripts/inspect_sft_full_encoding.py `
  --source data/raw/minimind/sft_t2t_mini.jsonl `
  --source-report ../experiments/sft_mini_data_inspection_v1/full_structure_v1/structure_report.json `
  --report-dir ../experiments/sft_mini_data_inspection_v1/full_encoding_preflight_v1 `
  --details-dir data/audit/sft_full_encoding_v1 `
  --workers 4 --chunk-size 1000
```

两个输出目录都拒绝覆盖；复跑必须一起换新版本。Windows 使用 spawn，每个 worker 独立加载本地 tokenizer，关闭 tokenizer 内部多线程，避免外层进程与内部线程同时争用资源。主进程最多提交 worker 数两倍的分块，按提交顺序收集，保持原始行序并限制在途内存。

原始文本不整文件装入内存，逐条诊断写盘；汇总只保留紧凑的长度、目标数组及少量最长/异常索引，不在内存堆积百万条原文或字典。全程没有模型加载、CUDA 计算、截断、padding、内容筛选或工具执行。

短段测量使用既有随机样本的 1,000 条，预热后单进程编码约 0.797 秒，即每秒约 1,255 条，直接外推约 12 分钟；该数字不包含全套诊断、进程启动和全部磁盘成本，也不保证全量内容分布与短段相同。本次使用 4 个 worker；最终实际耗时以报告为准。

## 3. 产物与状态

| 产物 | 位置与用途 |
| --- | --- |
| run_manifest.json | 本目录，记录 running/completed/failed、已处理数量、诊断状态和耗时 |
| report.json | 本目录，完成后保存整体与分组统计、最长及少量异常索引、输入/代码身份和大明细文件 hash |
| records.jsonl | implementation/data/audit/sft_full_encoding_v1，每个源行一条诊断，不保存完整原文或 token IDs |
| issues.jsonl | 同一忽略目录，保存所有触发本入口诊断的记录，不是已执行的排除清单 |

实际全量逐条明细为 181,028,384 字节（约 172.64 MiB），留在 Git 忽略的数据目录，不随汇总报告重复推送。异常明细为 0 字节，因为本次未检出对应诊断项。小型报告记录它们的路径、字节数和 SHA256；报告不是明细备份，保留或迁移大文件时要单独处理。

完成诊断且无标记时退出码为 0，有诊断标记时完成报告并以 2 退出。二者的 run_manifest 都应为 completed，diagnostic_status 另行区分结果。启动前身份不匹配会直接拒绝创建输出；进入运行状态后捕获到程序或身份错误时 manifest 为 failed，保留不完整明细供排查。进程被强杀或断电时可能来不及改状态，需要结合进程、日志和产物判断，不能把部分数量当作全量结果。

## 4. 验证与结论边界

入口先通过 4 项定向测试，覆盖原行身份、错误分类、shift 后目标口径、汇总、多进程输出顺序、异常明细、拒绝覆盖及来源身份不匹配。测试中有坏行的任务正常完成报告并返回 2，验证“诊断发现问题”和“程序运行失败”是不同状态。

随后全项目为 406 passed（94.93 秒；与全量诊断并行执行，耗时包含资源竞争）。运行结束又独立完成以下核对：

1. manifest 为 completed，最终报告 hash 与 manifest 一致，逐条明细/异常明细的字节数与 hash 一致。
2. 同时遍历原始文件和诊断明细，905,718 个源行号及原行 SHA256 逐条一致，无缺行、额外行或顺序错位；原始文件的整文件 hash 仍一致。
3. 重算输入位置、监督目标、诊断数量、形态数量与长度超限条数，均与汇总报告相符。三类数量仍为 plain 547,017、reasoning_only 273,869、tool_only 84,832。
4. 原固定随机样本的 1,000 条明细与全量输出逐条匹配，源行 hash、形态、标记、编码长度及有效目标数均一致；代码身份也再次核对一致。
