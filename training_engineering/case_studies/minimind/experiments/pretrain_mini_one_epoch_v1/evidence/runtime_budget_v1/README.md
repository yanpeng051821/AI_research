# MiniMind mini 预训练运行预算

> 结论：训练日志保留在 NVMe，checkpoint 写入 `E:` 机械硬盘；每 100 次 optimizer update 保存且全部保留；完整验证固定 `batch_size=4`，每 500 次更新运行，并保留初始与最终验证。

## 1. 目标设备

2026-10-24 识别到以下存储：

| 用途 | 设备 | 介质 | 容量与空间 |
| --- | --- | --- | --- |
| 代码、数据、日志 | `D:`，CF600 512GB | NVMe SSD | 分区 326.6 GiB，剩余约 57.4 GiB |
| checkpoint | `E:`，WD My Passport 2627 | USB HDD，NTFS | 1,863 GiB，剩余约 1,026.8 GiB |

正式 checkpoint 根目录确定为：

```text
E:\AI_research_checkpoints\minimind\pretrain_mini_one_epoch_v1
```

## 2. Checkpoint 测量

使用已有完整训练状态测得 checkpoint 大小约 773,267,947 bytes，即约 0.72 GiB。在 `E:` 上：

| 写入方式 | 耗时 |
| --- | ---: |
| 普通 `torch.save` | 22.36 秒 |
| `torch.save` 后 flush + `fsync` | 23.32 秒 |
| 紧接写入后的 SHA256 | 0.49 秒 |

正式实现采用同盘临时文件、flush、`fsync` 和原子替换，再计算 SHA256 并写 receipt。SHA256 是在同一份 773,267,947-byte 文件刚写完后测得的；此时系统页缓存仍然可用，与正式保存后立即生成 receipt 的执行顺序一致。按两项实测相加，单次完整保存约 23.81 秒。正式短跑仍会记录端到端的 `checkpoint_saved.seconds`，以校正模型序列化、机械盘波动和 receipt 写入带来的差异。

每 100 步保存时，最坏需要重算约 `100 × 11.33 / 60 = 18.9` 分钟。一个 epoch 在 step 100、200、……、4,900 以及最终 step 4,943 保存，共约 50 个 checkpoint，约占 36 GiB。机械盘空间充足，因此本轮全部保留，不引入滚动删除及其误删风险。

## 3. 验证 Batch 测量

在相同随机初始化、BF16 autocast 和验证集固定前 512 条记录上比较：

| batch | records/s | targets/s | 峰值 allocated | 设备空闲比例 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 61.97 | 11,763.22 | 0.55 GiB | 76.91% |
| 4 | **65.90** | **12,509.77** | 0.75 GiB | 73.05% |
| 8 | 62.02 | 11,772.35 | 1.14 GiB | 65.36% |
| 16 | 57.52 | 10,917.75 | 1.92 GiB | 49.70% |

`batch=4` 吞吐最高且显存余量充分，因此评测合同固定为 4。不同 batch 的 BF16 归约顺序会造成约 `1e-5` 的 NLL 差异，这也是 batch 必须进入评测合同的原因。

## 4. 完整验证测量

使用 `batch=4` 对冻结的全部 5,000 条验证记录执行一次随机初始化基线：

| 项目 | 结果 |
| --- | ---: |
| records | 5,000 |
| valid targets | 1,206,758 |
| validation NLL | 8.9122461692 |
| 耗时 | 76.86 秒 |
| records/s | 65.05 |
| targets/s | 15,700.45 |

初始化模型 SHA256 为 `272d31cc9061d16cf6a00f2486ba97de6777eda428fcd08c061faeb10cde1ab4`，与 micro-batch 基准中的模型身份一致。

## 5. 频率决定

完整验证安排为：

```text
step 0：初始基线
step 500, 1000, ..., 4500：周期验证 9 次
step 4943：最终验证
```

共 11 次，按实测约增加 14.1 分钟，即参数更新计算时间的约 1.5%。这能提供大约每 10% 训练进度一个同分布验证点。每一步的训练 loss、梯度范数和显存负责及时发现运行异常，完整验证不承担逐步健康检查。

参数更新计算约需 15.6 小时；checkpoint 预计增加约 19.8 分钟，验证约增加 14.1 分钟。三者都属于训练运行，合计得到当前端到端墙钟预算约 16.2 小时。这个数值仍需由完整配置短跑校正实际 GPU 序列化、机械盘波动和启动收尾开销。

## 6. 正式候选配方校正

2026-10-25 完成[正式配方暂停恢复短跑](../resume_gate_v1/README.md)，以下实测更新前述规划值：

| 项目 | 正式路径实测 | 单 epoch 外推 |
| --- | --- | --- |
| 数据准备及参数更新窗口 | 前 20 步平均 11.39 秒 | 4,943 步约 15.64 小时 |
| checkpoint 保存、SHA256 与 receipt | 24.62～24.89 秒 | 50 次约 20.6 分钟 |
| 完整验证 | 约 87 秒 | 11 次约 15.9 分钟 |
| 端到端训练运行 | 上述三项合计 | 约 16.3 小时 |

这里按不中断完成一个 epoch 估计。额外主动暂停和恢复会增加 checkpoint、恢复诊断验证与启动成本；数据长度变化、磁盘和系统竞争也可能影响速度。16.3 小时仍是短跑外推，不是完成时间保证。
