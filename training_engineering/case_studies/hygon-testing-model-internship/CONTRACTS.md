# 冻结与验收规范

[返回总览](README.md) · [执行指南](EXECUTION_GUIDE.md) · [技术参考](TECHNICAL_REFERENCE.md)

## 1. 职责分工

1. **实习生**：使用已交付工具执行、核对产物、抽样复核、记录故障和结果。
2. **课题准备方（导师/平台同事）**：选择、打包和验证已有工具，补齐必要的运行适配与说明。
   能复用官方或成熟框架时优先复用，不把工具缺口改成实习生开发任务。
3. **管理员**：确认设备分配、镜像、权限、持久盘和软件配套。
4. **导师**：确认任务、预算、数据规则和风险，批准阶段放行。
5. **复跑成员**：按团队交接记录重跑小型实验，验证可复用性。

本文只规定交付与检查方式，没有宣称下列工具已全部打包，也没有在 BW1000 上完成验证。

<a id="toolkit"></a>
## 2. 工具交付清单

### T1 环境探针
- **可复用**：管理员管理工具、PyTorch 设备接口、供应商自检。
- **待准备方交付**：固定命令集及小模型前向/反向/更新/加载探针；当前只有文档命令与检查要求。
- **完成标志**：在实际镜像可运行，输出版本、dtype、容差和结果，失败可定位。
- **使用阶段**：D1；实习生执行，不编写探针。

### T2 数据流水线
- **可复用**：现有 MiniMind 学习工程的 `minimind-audit`；CodeXGLUE 官方 `preprocess.py`。
- **已有边界**：现有 audit 负责结构检查，不代替去重、分组划分或 token 统计。
  现有 `prepare_pretrain_subset.py` 只打印抽样行号，不能当成完整子集导出器。
- **待准备方交付**：用现有数据处理库/团队工具组成下载、审计、去重、划分、统计、导出与校验的固定流水线，
  附版本、命令及产物示例。优先拼接成熟能力，不要求从零写一套系统。
- **完成标志**：合成异常样本和一份小公开样本可执行，行数对账、split 检查、重建检查通过。
- **使用阶段**：D2、D4、D5、D6；交付前可做下载盘点，不进入依赖它的训练。

### T3 训练与启动
- **可复用**：固定 MiniMind 的 `train_pretrain.py`、`train_full_sft.py`；
  后续选定框架的官方入口。
- **待准备方交付**：按实机验证的启动脚本、配置、初值留存/核对、日志归档和恢复命令。
  技术参考中的 Bash 范例是待验证模板，不是完整工具包。
- **完成标志**：不覆盖已有 run；实际命令、UTC 时间、退出码可查；
  声明 resume 时先确认文件存在与身份，避免上游静默从头训练。
- **使用阶段**：D2 起所有训练。

### T4 评测与比较
- **可复用**：团队已有 NLL/生成/配对评测能力，以及所选框架的评测接口。
- **待准备方交付**：对当前模型/tokenizer/字段格式验证过的批量入口，
  包含 NLL、固定生成、逐样本输出、完整性检查和分类指标。
- **完成标志**：合成数据证明 mask 与聚合正确；相同权重、合同和输入可重复；
  缺样本/重复 ID/错误合同会被标记，不被当作完整结果。
- **使用阶段**：D2 训练前就必须就绪，后续换框架重新验证。

### T5 观察与恢复
- **可复用**：已有 CPU 观察脚本和官方 resume；见[入口清单](TECHNICAL_REFERENCE.md#r7)。
- **待准备方交付**：实际训练路径的状态清点、短任务停止/恢复/比较方法和错误路径检查。
- **完成标志**：区分功能恢复与严格等价，给出已测范围；教学脚本成功不能替代官方入口验收。
- **使用阶段**：D3A/D3B；D6 在新框架重新验证。

### T6 团队配方
- **可复用**：前五项运行产物、配置及已有报告模板。
- **待交付**：`reports/team_handoff.md`，包括维护人、版本、命令、证据和限制。
- **完成标志**：另一位成员按记录完成 smoke，产物可校验。
- **使用阶段**：各阶段累计更新，项目结题必验。

工具准备状态统一记在 `reports/progress.md`：
`未准备 / 待实机验证 / 已交付 / 需更新`。每个“已交付”项必须有版本、说明和检查结果。
个人学习工程的依赖锁文件不是海光安装方案；既有 Python 脚本是否可迁移要先验证。

<a id="profiles"></a>
## 3. 运行分级

### 3.1 Smoke
F1～F8 仍全部核对，但可人工填写检查记录；不强制实现 preflight 程序或严格等价恢复。
目标是小样本、短时间、完成更新和评测。预算、退出记录、数据隔离及初值一致性不能省略。

### 3.2 Pilot
使用预计正式训练的模型、长度、精度与框架，测资源、保存和评测成本。
涉及续训时实际验证功能恢复，给出不支持的状态与风险。改变关键配置需重新验证。

### 3.3 正式运行
F1～F8、P1～P3 通过，有事前批准、基线和完整运行记录。
功能恢复通过才允许依赖它执行长任务；严格连续等价只在实验结论需要时额外要求。
现成工具能力不足时，由准备方调整工具或导师缩小任务，不交给实习生研发。

<a id="freeze"></a>
## 4. 训练前冻结清单

每次训练使用独立 `runs/<run_id>/`。保存以下文件，工具支持自动导出时优先自动导出；
否则按模板填写并复核，不能伪装成自动验证。

### F1 数据
- **证据**：`frozen/<version>/data_manifest.json`，split 映射和子集来源。
- **冻结**：文件 hash/条数、来源 revision、清洗/划分规则、seed、模板和长度处理。
- **检查**：重算实际训练/验证文件身份；检查 split 隔离及子集归属。
- **判定**：一致且来源可定位；拒绝覆盖旧版本。只读权限是辅助措施，不替代 hash 检查。

### F2 代码
- **证据**：`identity.json`，包含源码提交与工具包身份。
- **冻结**：官方提交、实际执行文件；有修改时附 patch 及新增文件清单/hash。
- **检查**：身份能重建当前工作树，记录未跟踪但参与执行的文件。
- **判定**：实际代码可恢复。无需为验收强行推到公开远端；使用团队批准的仓库或归档。

### F3 环境
- **证据**：`environment.json`、依赖快照、D1 批准记录。
- **冻结**：设备分配、Python、torch、驱动/DTK、精度、依赖、镜像 digest（适用时）。
- **检查**：与验证环境对照；裸机无镜像 digest 时写明不适用并保留安装来源。
- **判定**：关键变化已复核，未将“包名相同”当作后端兼容。

### F4 初值
- **证据**：`identity.json` 中模型来源、revision、文件 hash，`initialization_check.json`。
- **冻结**：随机初值文件或预训练 checkpoint；LoRA 还包含基座和 adapter 初始化设置。
- **检查**：留存权重与实际训练初值一致；不能用一个新随机模型冒充 B0。
- **判定**：明确文件身份；禁止只填容易变化的 `latest` 指针。

### F5 Tokenizer
- **证据**：`identity.json` 中 tokenizer 文件清单及 hash。
- **冻结**：词表、特殊 token、模板和相关配置。
- **检查**：数据统计、训练、评测使用对应版本；不同模型各自有独立冻结版本。
- **判定**：不存在无记录的模板、词表变化。

### F6 配置
- **证据**：`config.resolved.yaml` 或等价的完整 JSON，及其 hash。
- **冻结**：默认值展开后的模型/数据/优化器/LR/精度/batch/累积/seed/保存/恢复配置。
- **检查**：与 CLI、框架实际参数对照；同名参数优先级明确。
- **判定**：配置能解释真实行为。业务配置 hash 不等于数据内容 hash，两者都需要。

### F7 评测
- **证据**：`eval_contract.json`。
- **冻结**：数据身份、ID 集、模板、监督区间、生成预算、解码、停止、解析、指标与聚合。
- **检查**：比较双方引用相同合同，实际输入一致；只允许模型身份作为目标变化。
- **判定**：结果可配对。合同变化另开比较，未完成结果标 partial。

### F8 预期与预算
- **证据**：`expectation.json`，含填写时间、批准人、批准时间。
- **冻结**：工程验收、效果指标/有意义变化、允许回退、资源上限与停止条件。
- **检查**：正式训练前已确认；效果阈值依据开发基线和用途，不凭空承诺分数。
- **判定**：必填项完成且时间早于训练启动。Smoke 可以只验工程，但必须明确不声称效果成功。

<a id="preflight"></a>
## 5. 放行检查

### P1 身份检查
核对 F1～F7、路径、数据非空、权重结构、当前 run 未被其他训练占用。
每项记录 `pass/fail/not_applicable`、实际值、证据路径和检查方式。

### P2 资源检查
核对 F8、磁盘剩余、显存探针、最长样本、首次 optimizer step 和评测预算。
Smoke 可用 D1 的已批准小配置；正式规模必须有对应 pilot 证据。

### P3 人工批准
复核规则误伤、许可范围、基线是否足够、恢复限制及预算。
输出 `preflight.json`，字段 `overall_status` 使用 `pass/fail`，另记录检查人及各项证据；任一必须项失败则不启动。
首次可手工复核，自动化脚本是准备方的可选整合工作，不是实习生任务。

### 自动化规格
若团队后续整合 `preflight.py`，它应只读输入，输出结构化报告并在失败时返回非零退出码；
不修改 frozen、不替换配置、不下载未知权重、不自动启动训练。
需覆盖坏 hash、缺文件、空数据、配置冲突和失效批准。程序通过也不能替代 P3。

### 基线顺序
顺序固定为：准备工具与输入 → 冻结 F1～F8 → P1～P3 → 执行 B0 → 检查完整性 → 启动训练。
分类最终 test 不参与调参；先在开发集建立基线和冻结方案，最终同合同评测 B0/S1。

<a id="evidence"></a>
## 6. 证据与判定

### 6.1 最小运行目录

```text
runs/<run_id>/
├── command.sh
├── config.resolved.yaml
├── identity.json
├── environment.json
├── eval_contract.json
├── expectation.json
├── preflight.json
├── run_manifest.json
├── train.log
├── started_at.txt
├── finished_at.txt
├── exit_code.txt
├── artifacts.json
└── eval/
    ├── b0/
    └── trained/
```

框架原生日志/配置文件可直接引用，准备方负责说明字段对应关系，不要求实习生重复录入。
manifest 来不及写入时，用进程、退出文件和日志时间交叉确认，不能只看 running 状态。

### 6.2 数据对账
- 结构审计：原始物理行数 = 接受行数 + 拒绝行数。
- 去重：结构接受行数 = 去重保留数 + 重复移除数。
- 划分：去重保留数 = train + validation + test + 明确隔离数。
- 长度筛选：各 split 输入数 = 保留数 + 过滤数。
- 每一步都保留来源映射；跨阶段计数不能把同一个 duplicate 重复扣除。

### 6.3 重建与加载
数据在新临时目录重建，不删除原 frozen。比较内容 hash、split、规则、工具身份等稳定字段；
生成时间和绝对路径另列，不能要求它们逐字相同。

模型加载比较要声明 dtype、设备、eval 模式和容差。上游 FP16 导出与原精度训练参数不必逐 bit 相同；
先形成对应导出精度的参考再比较，差异过大交准备方定位，不通过放宽容差掩盖问题。

### 6.4 恢复等级
- **功能恢复**：现成入口恢复声明支持的训练状态，消费位置与 LR 可核对，后续参数继续更新。
- **严格等价**：同一完整计划下连续与中断恢复路径的样本、随机性、状态和参数满足预设对照要求。
- 没有第二种证据就只声明第一种；模型导出文件本身不等于可续训 checkpoint。
- D4 长任务至少需要功能恢复和风险批准；涉及严格等价的研究结论另加验收。

### 6.5 效果与团队验收
工程完成、效果达标、团队可复用是三个独立结论。
效果没有提升可以完成一次可信实验，但报告应明确“不达效果标准”。
团队复用还需另一位成员成功复跑 smoke，并留下版本、命令、结果和修订记录。
因果性声明需要相应受控实验，不把消融一律降为可有可无的加分项。

## 7. 归档与维护

1. 每个 demo 写一份结论在前的报告：结论、目标、版本、命令、结果、故障、限制、下一步。
2. 小型报告/配置/清单进入团队仓库；大数据/权重进入批准的持久存储，记录 hash。
3. 保留至少一份独立备份并验证可读取；同盘复制不是独立备份。
4. 更新 `reports/team_handoff.md`，引用原证据，不再建多份平行路线表。
5. 改模型、数据、设备或框架时，按影响重新验收，不把上一次的通过状态自动继承。
