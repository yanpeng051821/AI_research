# 实习执行指南

[返回总览](README.md) · [冻结与验收规范](CONTRACTS.md) · [技术参考](TECHNICAL_REFERENCE.md)

## 使用规则

### 1. 路径与职责

按编号步骤执行，在 `implementation/reports/progress.md` 记录当前步骤、证据路径和阻塞项。
本指南中的 `docs/`、`scripts/`、`reports/` 均相对未来的 `implementation/`；
`raw/`、`staging/`、`frozen/`、`runs/` 相对管理员确认的 `LAB_ROOT`。
这些产物路径是执行后应形成的文件，不是本次已创建的文件。
**实习生只执行已有工具、选择批准的配置、核对结果和记录经验，不开发脚本或框架。**
每个阶段先查[工具交付清单](CONTRACTS.md#toolkit)；未交付工具由导师/平台负责人准备，不能把缺口转成实习生开发作业。

### 2. 验收类型

验收类型：**自动**由脚本/测试检查，**复核**由指定人员看证据，**现场**检查理解。
“必须”项失败就停在本阶段；“应该”项可由导师批准带缺口推进，并记录原因、影响和补齐日期。
现场问答不替代自动检查，自动检查也不代替数据质量判断。

### 3. 参考投入

以下估计仅用于排期，从工具包已交付起计算，不含管理员排障或工具准备；每阶段开始前由导师调整。

- D0 任务与工作区：0.5–1 天。
- D1 海光环境：1–3 天。
- D2 小规模预训练：2–4 天。
- D3A 训练观测：0.5–1 天。
- D3B 恢复验证：1–2 天。
- D4 扩大预训练：2–5 天工程投入，加实测训练时间。
- D5 通用 SFT：3–7 天。
- D6 缺陷分类：1–3 周。
- D7 阶段选择：半天决策。

它们不是完成承诺。首次训练者需要更久时调整范围，不以跳过检查赶进度。

### 4. 求助规则

1. 同一问题排查半个工作日仍无进展，提交错误栈、版本、复现命令和已尝试方法。
2. 超过 1 个工作日仍受阻，由导师或管理员共同定位。
3. 驱动、磁盘、权限问题直接找管理员。
4. 数据泄漏、NaN、文件损坏及超预算风险立即停下相关运行。

## D0 任务与工作区

### 目标
确定任务边界和持久存储。本阶段不使用加速卡。

### 前置条件
- [ ] 有服务器管理员和导师联系人；已确认当前使用公开数据。

### 输入
现有服务器信息、本手册、[存储与版本命令](TECHNICAL_REFERENCE.md#r1)。

### 步骤
1. **D0-S1 任务**：创建 `docs/task.md`，写输入、输出、非目标、工程成功条件；
   标明 Devign 是待确认候选，记录导师是否同意。产物：任务卡及确认记录。
2. **D0-S2 存储**：向管理员确认持久盘，用 `df -h`/`findmnt` 核对；建立参考目录。
   产物：`docs/storage.md`，含代码/原始数据/冻结数据/运行产物路径、容量、保留规则及管理员确认。
3. **D0-S3 版本**：获取固定 MiniMind 提交，记录 `git rev-parse HEAD`。
   产物：`docs/references.md`；代码版本与数据版本分开填写。
4. **D0-S4 计划**：创建 `reports/progress.md`，记录步骤、状态、证据链接、负责人和下次检查时间；
   创建 `docs/budget.md`，填写首轮运行时限与审批方式。

### 产出
`docs/{task,storage,references,budget}.md`；`reports/progress.md`；持久盘目录。

### 验收
- **D0-A1 必须/复核**：任务卡包含输入、输出和非目标，导师确认可查。对应 S1。
- **D0-A2 必须/复核**：四类路径和保留规则齐全，挂载检查与管理员确认一致。对应 S2。
- **D0-A3 必须/自动**：实际源码提交等于 references 记录。对应 S3。
- **D0-A4 必须/复核**：首轮预算责任人、时限和下一次检查已填写，无“待定”冒充批准。对应 S4。

### 说明
长期实习不等于无限训练预算。后续逐阶段审批，不需要现在预测全部模型或数据规模。

<a id="d1"></a>
## D1 海光环境

### 目标
证明分配到的设备可以正确完成一次训练更新，而不只是安装了 PyTorch。

### 前置条件
- [ ] D0-A1～A4 通过；管理员提供可用环境和设备访问方式。

### 输入
固定源码、管理员配套说明、[设备与依赖检查](TECHNICAL_REFERENCE.md#r2)。

### 步骤
1. **D1-S1 盘点**：执行只读设备探针，记录可见卡数、每卡总显存、空闲量、已有占用和版本。
   产物：`reports/demo01/device.txt`，管理员工具输出与 PyTorch 输出分别保存。
2. **D1-S2 环境**：保留海光 torch，按需安装最小依赖；记录安装前后包列表并执行 `pip check`。
   产物：`docs/environment.md`、`reports/demo01/{packages_before,packages_after}.txt`。
3. **D1-S3 数值**：运行准备方交付的[设备探针](TECHNICAL_REFERENCE.md#r2)，
   先 CPU/设备 FP32，再测拟用低精度，覆盖前向、梯度、一次 AdamW 更新及加载。
   产物：工具版本、测试输出、`reports/demo01/probe.json`，逐项记录 dtype、容差与结果。
4. **D1-S4 决策**：指定本轮可用设备、dtype、算子路径；不支持的功能保留关闭。
   产物：`reports/demo01/approval.md`，列出通过配置与已知限制。

### 产出
设备原始输出、环境说明、依赖快照、探针版本与结果、批准配置。

### 验收
- **D1-A1 必须/复核**：分配卡数与可见卡数已解释；显存单位和总量/空闲量分开记录。对应 S1。
- **D1-A2 必须/自动+复核**：`pip check` 成功，torch 来源和版本符合配套说明。对应 S2。
- **D1-A3 必须/自动**：批准精度下结果有限、参数更新、数值容差检查和加载检查均通过。对应 S3。
- **D1-A4 必须/复核**：approval 引用实际结果，不用 CPU 成功代替设备成功。对应 S4。

### 说明
查卡接口名字里有 CUDA 不代表 NVIDIA 硬件。若设备不可见，先查环境映射与权限，见技术参考。

<a id="d2"></a>
## D2 小规模预训练

### 目标
复用官方入口，用固定 128 条 train 样本完成 smoke、基线及训练后评测。

### 前置条件
- [ ] D1-A1～A4 通过；数据/评测/启动工具包已按 [T2～T4](CONTRACTS.md#toolkit)交付。
- [ ] 使用 [smoke 冻结规则](CONTRACTS.md#profiles)，暂不要求严格断点恢复。

### 输入
固定 MiniMind、`pretrain_t2t_mini.jsonl`、tokenizer 和团队工具包；[数据细则](TECHNICAL_REFERENCE.md#r3)。

### 步骤
1. **D2-S1 获取**：固定 revision，下载原文件并运行校验；保存来源、hash、字节数、物理行数。
   产物：`raw/minimind/<revision>/`、`source_manifest.json`。
2. **D2-S2 审计**：运行现有审计入口，再运行交付的去重流程，查看异常记录并抽检。
   产物：`staging/mm-pt-v1/audit/`、`dedup/`。原始审计与去重分开对账。
3. **D2-S3 划分**：用交付流程按来源/内容组划分，固定 seed，从 train 抽取 128 条。
   产物：split、`split_manifest.jsonl`、交集检查；不足 128 条时找导师调整范围。
4. **D2-S4 统计**：运行 token/labels 统计与样本展示，核对三条样本。
   产物：`stats_report.json`、`label_check.md`。
5. **D2-S5 冻结**：运行交付的导出/校验流程，生成 `frozen/mm-pt-v1/`；
   在新临时目录重建并比较稳定身份。产物：manifest 和 `rebuild_check.json`，保留原 frozen。
6. **D2-S6 初值**：调用工具包保存实际初始权重、核对与训练入口初值一致；
   运行已有评测自检，不编写评测器。产物：`init_weight.pt`、`initialization_check.json`、评测自检记录。
7. **D2-S7 放行**：新建 run，填 F1～F8，完成 P1～P3；首次 smoke 可按清单人工核对。
   产物：运行文件集、`preflight.json`、导师确认。
8. **D2-S8 基线**：运行交付的批量评测入口，得到 `eval/b0/`，检查完整性。
9. **D2-S9 训练**：审查准备方交付的启动脚本，通过 Bash 调用官方入口；[模板说明](TECHNICAL_REFERENCE.md#r5)。
   产物：实际命令、UTC 时间、日志、退出码及权重位置。
10. **D2-S10 对照**：调用加载检查及同合同评测，生成 `eval/smoke/`、
    `reload_check.json`、`comparison.json` 和 `artifacts.json`。

### 产出
冻结数据、工具版本、自检结果、运行文件集、B0/训练后结果；`reports/demo02/README.md`。

### 验收
- **D2-A1 必须/自动**：原始行数 = 审计接受 + 审计拒绝；审计接受 = 去重保留 + 重复移除。
  来源映射不丢失。对应 S1～S2。
- **D2-A2 必须/自动**：split 组 ID/完全重复内容交集为空，128 条 smoke 属于 train。对应 S3。
- **D2-A3 必须/自动+复核**：统计可重算，标签正确；重建数据及稳定身份匹配，时间/路径差异单列。对应 S4～S5。
- **D2-A4 必须/自动**：工具自检通过，实际初值与留存初值一致。对应 S6。
- **D2-A5 必须/复核**：F1～F8、P1～P3 的 smoke 要求通过，B0 在训练开始前完成。对应 S7～S8。
- **D2-A6 必须/自动**：退出码 0；128 条、batch 2、accumulation 1、epoch 1 时完成 64 次更新。对应 S9。
- **D2-A7 必须/自动**：加载按导出精度容差通过，两次评测合同及 ID 集相同，结果完整。对应 S10。
- **D2-A8 必须/复核**：接受/拒绝样本各固定抽查最多 20 条，不足取全部，保留处理意见。对应 S2、S4。

### 说明
现有审计工具没有去重能力时，不能把它的 accepted 直接解释为去重保留数。
评测工具未交付时停在训练前，而不是让实习生现场开发。smoke 不以聊天质量为验收目标。

<a id="d3a"></a>
## D3A 训练观测

### 目标
理解现成训练流程的关键日志和计算口径，为团队留下可解释的运行记录。

### 前置条件
- [ ] D2 必须项通过；已有实际 smoke 日志和已交付观察工具。

### 输入
[固定提交行为](TECHNICAL_REFERENCE.md#r6)、D2 日志、[已有观察脚本](TECHNICAL_REFERENCE.md#r7)。

### 步骤
1. **D3A-S1 定位**：按准备方给出的源码位置查看 loss、梯度累积、optimizer 和 LR；
   在 `reports/demo03/upstream_behavior.md` 记录含义及证据，不要求重写。
2. **D3A-S2 观察**：运行已有的累积、裁剪、LR 小实验，核对输出。
   产物：工具版本、命令和输出；这些教学例子不是官方 GPU 路径的替代验收。
3. **D3A-S3 对账**：从实际 smoke 日志核对 micro-step、optimizer 更新、样本数和 LR；
   对不等 token/尾部窗口记录官方行为及适用限制。产物：`log_review.md`。
4. **D3A-S4 配方**：为下一轮选择明确的官方配置，或选择团队已验证的框架配置；
   若需补丁，由准备方提供并重新验证。产物：代码身份、配置和变更说明。

### 产出
上游行为说明、观察输出、日志对账、下一轮配置；不产出自研训练器。

### 验收
- **D3A-A1 必须/复核**：各项说明有固定源码位置，step/loss/LR 口径写清。对应 S1。
- **D3A-A2 必须/自动+复核**：已有观察工具成功运行，实习生记录结果而非照抄公式。对应 S2。
- **D3A-A3 必须/复核**：实际日志对账无未解释差异，尾部及归一化限制已记入报告。对应 S3。
- **D3A-A4 必须/复核**：选用配方可追溯，采用与上游不同的语义时有准备方验证证据。对应 S4。
- **D3A-A5 现场**：指定一条日志说明其分母、更新次数和 LR 含义，单独记录问答。对应 S1～S3。

### 说明
本阶段目标是会运行、会检查、会解释，不强制把上游改成另一套算法。
同一对照中的各组必须使用一致计算口径；具体区别见技术参考。

<a id="d3b"></a>
## D3B 恢复验证

### 目标
用选定入口实际完成一次保存、停止、续训，并准确声明恢复能力。

### 前置条件
- [ ] D3A 通过；准备方给出该版本的保存位置、恢复命令和安全停止方式。

### 输入
官方或成熟框架的恢复入口、固定小数据与完整训练计划；[恢复细则](TECHNICAL_REFERENCE.md#r8)。

### 步骤
1. **D3B-S1 清点**：检查 checkpoint 是否有模型、optimizer、步数、精度状态以及该实现支持的其他状态。
   产物：`checkpoint_inventory.json`，对 RNG/数据状态等缺项如实记录。
2. **D3B-S2 续训**：在小任务中保存一个完整 checkpoint，按交付方法停止；
   使用同一完整计划在新进程恢复，核对起始位置、optimizer/LR 状态及后续更新。
   产物：停止前后日志、`resume_check.json`。
3. **D3B-S3 对照**：运行准备方提供的连续/恢复比较工具；
   比较消费位置、LR、参数偏差，按证据标为“功能恢复”或“严格等价恢复”。
   产物：`resume_comparison.json`；无严格证据时不要求实习生补写实现。
4. **D3B-S4 故障**：用副本验证错误路径、缺失文件和不完整快照的处理；
   上游缺文件会静默新训时，由交付启动检查拦截。产物：故障检查记录。
5. **D3B-S5 放行**：导师确认实际恢复能力、风险和适用范围，批准后才能长时间运行。
   产物：`reports/demo03/resume_approval.md`。

### 产出
保存/恢复命令、状态清单、实际续训和对照证据、风险确认。

### 验收
- **D3B-A1 必须/自动+复核**：完整 checkpoint 可加载，模型和 optimizer 等核心状态确实恢复，后续参数继续更新。对应 S1～S2。
- **D3B-A2 必须/复核**：实际恢复的数据位置和 LR 符合已声明语义，缺项、偏差和影响均有证据。对应 S2～S3。
- **D3B-A3 必须/自动**：交付流程可阻止错误 checkpoint 被当成合法恢复或无提示从头开始。对应 S4。
- **D3B-A4 必须/复核**：批准范围与正式设备/配置匹配；仅功能恢复时明确不声称严格连续等价。对应 S5。
- **D3B-A5 条件必须/自动**：只有结论依赖严格恢复等价时，才要求完整 RNG/顺序及连续/恢复容差测试通过。对应 S3。

### 说明
功能恢复是能按声明的状态继续训练，严格等价还要求与未中断路径对齐。
两者不能混称；完整训练流程的入门验收不强制研发第二种能力。

<a id="d4"></a>
## D4 扩大预训练

### 目标
按实测资源扩大一个冻结配置，而不是盲目跑完整个下载文件。

### 前置条件
- [ ] D3A 通过；D3B 功能恢复可在 S3 pilot 中一并验证，S4 正式运行前必须通过。
- [ ] 有阶段预算负责人。

### 输入
冻结 train 候选、[token 预算与对照细则](TECHNICAL_REFERENCE.md#r9)、选定训练实现。

### 步骤
1. **D4-S1 数据**：扩展嵌套 train 子集，核对与评测集的重叠，生成新数据版本；
   报告独立 token 与计划重复消费 token。产物：manifest 和长度/来源统计。
2. **D4-S2 探针**：测实际模型参数量、最长允许序列、第一次 optimizer step、吞吐与保存空间。
   产物：`capacity_probe.json` 和时间/磁盘预算；导师批准规模。
3. **D4-S3 Pilot**：通过 F1～F8 与 P1～P3，跑批准的短 pilot；
   测稳定吞吐并完成 D3B。产物：pilot 目录、恢复结果和正式运行放行记录。
4. **D4-S4 正式**：创建新 run，从声明初值开始；重复冻结检查与同合同 B0，
   完成训练、加载、验证、备份。产物：正式运行证据集。
5. **D4-S5 对照**：导师批准一个变量与预算，例如等消费 token 下“小子集重复/大子集”；
   独立冻结并运行两组，对比效果和成本。产物：`reports/demo04/ablation.md`；预算不足时记为延期。

### 产出
数据版本、容量探针、pilot/正式运行文件、恢复批准、预算与可选对照报告。

### 验收
- **D4-A1 必须/自动**：数据身份与统计可重算，评测集隔离成立。对应 S1。
- **D4-A2 必须/复核**：预算用实际吞吐和保存/评测开销估算，批准记录早于正式训练。对应 S2～S3。
- **D4-A3 必须/自动+复核**：D3B 必须项、F1～F8、P1～P3 全部通过；实际配置未越出验证范围。对应 S3～S4。
- **D4-A4 必须/自动**：正式消费量/更新数符合合同，退出正常，评测完整，备份校验通过。对应 S4。
- **D4-A5 条件必须/复核**：若宣称某因素带来改善，必须有对应受控对照；没做 S5 只报告本次运行结果。对应 S5。

### 说明
数据量实验与等算力实验不是同一问题。大文件完整训练可延后，受控实验也不能从两三个点外推 scaling law。

<a id="d5"></a>
## D5 通用 SFT

### 目标
正确交接 PT 权重与消息数据，验证监督范围并检查能力变化。

### 前置条件
- [ ] D3A/D3B 通过；选定 PT 权重可加载。
- [ ] 可使用已验收的小规模 PT 产物；若省略 D4 大训练，记录原因和能力限制。

### 输入
固定 `sft_t2t_mini.jsonl`、PT 权重和 tokenizer；[SFT 操作细则](TECHNICAL_REFERENCE.md#r10)。

### 步骤
1. **D5-S1 数据**：审计消息、角色、会话分组、重复和长样本，冻结 `mm-sft-v1`。
   产物：manifest、分组检查、过滤统计与抽检记录。
2. **D5-S2 监督**：运行交付的单轮/多轮/system/长度边界检查；定位 assistant 与结束标记，验证集使用固定处理。
   产物：mask 测试、标签可视检查和确定性检查。
3. **D5-S3 交接**：明确 PT checkpoint hash，核对结构/词表/加载 keys；新建 SFT optimizer 与计划。
   产物：`initialization_check.json`；本轮是新阶段，不是 PT 续训。
4. **D5-S4 基线**：冻结运行与评测合同，跑训练前的 SFT 验证 NLL、保留文本 NLL和固定生成。
   产物：preflight、`eval/b0/`。
5. **D5-S5 训练**：小 batch 过拟合、smoke、pilot 后批准正式运行；各 run 独立留存，正式配置重做放行。
   产物：日志、checkpoint、状态、预算与加载结果。
6. **D5-S6 对照**：同合同评测、按 ID 比较输出和回退，备份。
   产物：`eval/s1/`、comparison、`reports/demo05/README.md`。

### 产出
消息数据版本、mask 测试、阶段身份、所有运行证据、配对评测与备份清单。

### 验收
- **D5-A1 必须/自动+复核**：会话隔离、非零监督、结束边界和随机性检查通过。对应 S1～S2。
- **D5-A2 必须/自动**：权重/结构匹配，阶段初值和新 optimizer 可查。对应 S3。
- **D5-A3 必须/自动+复核**：F1～F8、P1～P3 通过；正式训练前已完成 B0；恢复能力覆盖实际配置。对应 S4～S5。
- **D5-A4 必须/自动**：逐样本结果完整、合同 hash 一致，SFT NLL 与文本 NLL 分别比较。对应 S6。
- **D5-A5 必须/复核**：改善/回退的固定抽样有记录，报告不把不同监督范围的训练 loss 直接比较。对应 S6。

### 说明
SFT 验证集 NLL 改善不等于所有任务改善；训练后生成必须记录长度上限和停止原因。

<a id="d6"></a>
## D6 缺陷分类

### 目标
以公开代码缺陷分类完成一次客观可评测的领域 SFT，不承诺一定提升。

### 前置条件
- [ ] D5 通过；导师确认 Devign 任务及数据使用范围。
- [ ] 准备采用海光验证过的成熟框架，具体版本在本阶段固定。

### 输入
官方数据及 split、候选代码/指令模型、[任务与数据细则](TECHNICAL_REFERENCE.md#r11)。

### 步骤
1. **D6-S1 数据**：固定来源代码和下载文件，按官方索引预处理，审计重复、标签、长度与许可。
   转会话但不制造根因标签。产物：`frozen/devign-sft-v1/`、coverage 与审计报告。
2. **D6-S2 框架**：冻结模型 revision、tokenizer、成熟框架版本、全参/LoRA 方案；
   运行准备方提供的该框架 mask/loss/更新检查与 D3B 功能恢复检查，不自行扩展 MiniMind trainer。
   产物：`framework_alignment.md`、兼容性及恢复测试。
3. **D6-S3 基线**：在开发集跑多数类与 B0，估算评测成本，冻结解析及生成合同；
   最终 test 只在方案确定后使用。产物：`eval/dev_b0/`、开发基线报告。
4. **D6-S4 预注册**：在正式训练前填写目标指标、有意义提升量、允许回退/invalid 上限、预算和停止条件；
   阈值依据开发基线、样本量和用途，经导师确认。产物：`expectation.json`。
5. **D6-S5 训练**：F1～F8、P1～P3 放行，过拟合/smoke/pilot 后运行正式 SFT。
   产物：完整训练、恢复、加载证据；LoRA 保存 adapter 和基座身份。
6. **D6-S6 评测**：开发集选定方案后，在相同最终合同下评测 B0/S1；
   保留 invalid、计算 macro-F1/accuracy、按 ID 配对，完成固定分层抽检与备份。
   产物：`eval/test_b0/`、`eval/test_s1/`、comparison、错误分析。
7. **D6-S7 决策**：分别判定工程验收与任务效果验收；效果不达标仍保留负结果，决定停下或提出新假设。
   产物：`reports/demo06/README.md`，后续修改明确为新实验。

### 产出
数据合同、框架验证、基线、事前预期、SFT 与最终配对评测、效果决策。

### 验收
- **D6-A1 必须/自动+复核**：官方索引可追溯、标签未混入推断输入、过滤覆盖率与类别比例可查。对应 S1。
- **D6-A2 必须/自动+复核**：当前框架实际计算/恢复路径通过已交付检查，版本与代码身份冻结。对应 S2。
- **D6-A3 必须/复核**：预期基于开发证据并在正式训练前批准，最终测试未用于选阈值。对应 S3～S4。
- **D6-A4 必须/自动**：F1～F8、P1～P3 通过，更新/保存/重新加载完成。对应 S5。
- **D6-A5 必须/自动**：两侧 ID、合同一致，结果完整；invalid 未被剔除，分类指标可从原始输出重算。对应 S6。
- **D6-A6 必须/复核**：工程结论、效果结论、成本与限制分别填写；未达到阈值时不标效果通过。对应 S7。

### 说明
未核验的“某数据集普遍只能达到多少分”不作为目标依据。
换模型或框架需要新验证；这里迁移检查方法，不强制复用 MiniMind 的模型类和训练循环。

<a id="d7"></a>
## D7 阶段选择

### 目标
以实际错误确定下一步，而不是默认继续所有算法。

### 前置条件
- [ ] D6 已有完整结果或明确的停止原因。

### 输入
错误分析、成本与限制；[后续阶段参考](TECHNICAL_REFERENCE.md#r12)。

### 步骤
1. **D7-S1 诊断**：列出主要错误、支持证据、尚无法确定的原因。
2. **D7-S2 选择**：选择修数据/提示/评测、补对照、CPT、DPO、可验证奖励或暂不训练之一。
3. **D7-S3 立项**：若继续训练，另写目标、数据依据、可比较基线、预算及新的冻结合同；
   没有数据/奖励条件时先做可行性验证。

### 产出
`reports/demo07/decision.md`；必要时新增实验任务卡。

### 验收
- **D7-A1 必须/复核**：建议对应具体错误证据，而不是算法热度。对应 S1～S2。
- **D7-A2 必须/复核**：下一阶段所需数据/偏好/验证器已核实，未满足项有明确可行性任务。对应 S3。

### 说明
分类标签不自动构成高质量偏好数据，代码可运行也不自动构成可靠奖励。
允许决定“不新增训练”，不影响已完成工程的结题。

<a id="handoff"></a>
## 团队交接

### 1. 每阶段归档

完成各 demo 后，更新同一个 `reports/team_handoff.md`，引用现有证据，不重复抄写报告。
按环境、数据、运行、评测、故障、适用边界分类；每项写明已验证版本、复现命令、结果位置和维护人。
未验证建议单独列出，不与已成功配方混放。

### 2. 独立复跑

由另一位团队成员按交接记录，在批准环境运行一个小型 smoke；原执行者只解答记录遗漏。
保存操作者、工具包版本、配置、命令、退出码、权重加载及评测完整性结果。
遇到缺漏先修记录或由准备方修工具，再复跑；不要求第二位成员重写代码。

### 3. 团队验收

- **H-A1 必须/复核**：环境、数据、启动、恢复、评测均有可定位的配方与证据。
- **H-A2 必须/自动+复核**：另一位成员的 smoke 完成，产物通过同一小型验收合同。
- **H-A3 必须/复核**：明确哪些资产可复用，哪些需要随模型、数据、设备或任务重新验证。
- **H-A4 必须/复核**：面向专用模型的下一阶段问题清单已写出，未把通用练习分数当作业务有效性。
